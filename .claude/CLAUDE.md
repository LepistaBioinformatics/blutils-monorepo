# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

This is a **monorepo aggregator** for the Blutils project. It contains almost no
code of its own — the real work lives in two git submodules under `modules/`:

- `modules/blutils` — the Rust engine ([LepistaBioinformatics/blutils](https://github.com/LepistaBioinformatics/blutils))
- `modules/blutils-ui` — the React result viewer ([LepistaBioinformatics/blutils-ui](https://github.com/LepistaBioinformatics/blutils-ui))

The two are decoupled at runtime: the CLI produces a serialized result file and
the UI consumes it. They share no build system and never import each other —
**the only contract between them is the JSON/YAML output schema** (see below). The viewer
reads JSON only; the engine also emits JSONL and YAML (via `serde_yaml_ng`).

## Working with submodules

The submodules are pinned to specific commits. Always be explicit about which
one you are operating in.

```bash
git submodule update --init --recursive   # first checkout / refresh pins
git submodule update --remote modules/blutils-ui   # bump a single module to its upstream tip
```

Edits inside a submodule are commits in that submodule's own repository; the
monorepo only records the pinned commit hash. To land a change end-to-end:
commit/push inside the submodule first, then commit the updated pointer here.

## modules/blutils — Rust engine

Cargo workspace (`modules/blutils/Cargo.toml`) following **hexagonal / clean
architecture**. Members:

- `core/` (`blutils-core`) — domain + use cases. No I/O side effects beyond what
  the adapters provide. Layout: `core/src/domain/{entities,dtos,utils}` and
  `core/src/use_cases/`. The use case directory names ARE the feature catalog
  (`run_blast_and_build_consensus`, `build_consensus_identities`,
  `build_blutils_db_from_ncbi_files`, `build_qiime_db_from_blutils_db`,
  `build_kraken_db_from_ncbi_files`, `parse_consensus_as_tabular`).
- `ports/cli/` (`blutils-cli`) — the `blu` binary, the only user-facing entry
  point. Uses `clap` (derive). Subcommands: `build-db`, `blastn`, `check`.
- `adapters/proc/` (`blutils-proc-adapter`) — shells out to the external
  `ncbi-blast+` toolchain via `subprocess`. This is where the actual `blastn`
  process invocation lives.

Dependency direction is `ports/cli → core` and `ports/cli → adapters/proc`;
`core` depends on neither. Keep new business logic in `core/use_cases`, keep
external-process concerns in `adapters/proc`, keep `ports/cli` thin (arg parsing
+ wiring only).

Runtime prerequisite: **NCBI BLAST+ must be installed on the host** — `blu check
linux` verifies it. Heavy data work uses `polars` and parallelism uses `rayon`.

### Commands (run inside `modules/blutils`)

```bash
cargo build --release            # build the whole workspace
cargo run -p blutils-cli -- --help
cargo test                       # all workspace tests
cargo test -p blutils-core       # one crate
cargo test <test_name>           # a single test by name
cargo fmt                        # respects .rustfmt.toml
cargo clippy --all-targets
```

Versioning is workspace-shared (`shared-version = true`) via `cargo-release`,
and `CHANGELOG.md` is generated by `git-cliff` (config in `cliff.toml`) as a
pre-release hook. Bump versions through the release tooling, not by hand.

## modules/blutils-ui — React result viewer

Create-React-App driven through **CRACO** (`craco.config.js`), TypeScript,
TailwindCSS + `flowbite-react`. It is a static, client-side-only viewer
(deployed to GitHub Pages via `gh-pages`) — there is no backend; the user loads a
Blutils output file and the app renders/groups/paginates it.

Key code: `src/types/BlutilsResult.ts` is the consumed data contract;
`src/pages`, `src/components`, `src/functions` (e.g. `kebab-to-scientific-name`)
handle rendering of taxonomic results.

### Commands (run inside `modules/blutils-ui`)

```bash
yarn install
yarn start            # dev server (craco start)
yarn build            # production build (craco build)
yarn test             # craco test (Jest + Testing Library, watch mode)
yarn test -- --watchAll=false   # single CI-style run
yarn deploy           # build + publish to GitHub Pages
```

## The data contract (the link between the two modules)

This is the single most important cross-module fact. The Rust `BlutilsOutput`
(`core/src/domain/dtos/blutils_output.rs`) is serialized with
`#[serde(rename_all = "camelCase")]` and mirrored field-for-field by the
TypeScript `BlutilsResult` interface (`blutils-ui/src/types/BlutilsResult.ts`):

```
BlutilsOutput { results: [QueryWithConsensus], config: BlastBuilder }
        ⇅  (JSON / YAML, camelCase)
BlutilsResult { results: [Result],            config: Config }
```

The consensus payload (`taxon`, `consensusBeans`, `reachedRank`, `percIdentity`,
`taxonomy`, …) must stay structurally identical on both sides. **If you change a
serialized field in `core/src/domain/dtos`, you must update the matching field in
`blutils-ui/src/types/BlutilsResult.ts`, and vice versa** — a silent mismatch
here breaks the viewer with no compile error. Field names use camelCase because
of the serde attribute; preserve that when adding fields.
